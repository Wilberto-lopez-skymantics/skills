What makes this a Personal Implementation?

By Wilberto Lopez / Skymantics

While Spec-Driven Development is a broad industry concept, this repository represents my own opinionated, production-tested methodology. Traditional AI agent setups rely on opaque, non-auditable global system prompts or platform-specific IDE plugins.

This personal implementation fuses SDD with research from the Interpretable Context Methodology (ICM) paper ("If the context is interpretable, the agent is steerable"). By embedding the entire multi-stage pipeline, adversarial review swarms, token audit rules, and defect backpropagation loops directly into the project's filesystem inside specs/.sdd/, any AI agent (Cursor, Gemini CLI, Claude Code, ChatGPT, Llama) can execute the pipeline perfectly with zero global configuration lock-in.

Core Spec Theory

From Requirements to Invariants (§V)

Understanding the fundamental distinction between loose user requirements and formal spec invariants, and how the SDD pipeline converts high-level intent into mathematical invariants in specs/SPEC.md.

📋 User Requirement

Stage 01 Input

A high-level statement of user intent, capability, or functional goal written in natural language.

  • Focus: What the system should do when everything goes right (happy path).
  • Format: Natural prose, user story ("As a user, I want..."), or feature brief.
  • Vulnerability: Often ambiguous, underspecified, leaves boundaries open to interpretation, and fails to declare error bounds or edge-case behavior.
  • Example: "Users can upload profile avatar pictures up to 5MB."

🛡️ System Invariant (§V)

SPEC.md Invariant

A formal, non-negotiable mathematical assertion or boundary property that MUST NEVER be violated under any state transition.

  • Focus: What MUST ALWAYS hold true across all execution paths, error states, and attack attempts.
  • Format: Formal assertion ($V_1, V_2, \dots, V_n$), explicit constraints, binary validation rules.
  • Power: Unbreakable execution guardrail. If an invariant fails, runtime/tests halt immediately; code generation is rejected.
  • Example: "$V_1$: file.size <= 5,242,880 B AND $V_2$: magic_bytes IN [FF D8 FF, 89 50 4E 47] AND $V_3$: file_extension IN ['.jpg', '.png']."

The Transformation Pipeline: Requirement → Invariant

How raw ideas pass through the SDD stage gates to become hardened invariants in specs/SPEC.md:

1

Brainstorming & Extraction (Stage 01)

Gather informal requirements from the user. Run Confidence Self-Assessment (≥ 85%) to clarify ambiguities and identify core system inputs and state targets.

2

Adversarial Red Team Attack (Stage 02)

The Critic Council attacks the requirement with boundary probes, malicious inputs, concurrency races, and null states. Every discovered flaw is converted into a formal invariant rule ($V_n$).

3

Defect Backpropagation (Stage 00)

If a defect ever escapes in testing or production, Stage 00 traces which invariant was missing, logs it in backprop-log.md, and appends a new mandatory invariant ($V_{n+1}$) to SPEC.md.

Real-World Transformation Example: Password Reset Token specs/SPEC.md §V Invariants
❌ Raw Requirement (Informal Intent) 
"Users can request a password reset email containing a link to reset their account password."
✅ Transformed Invariants in SPEC.md (§V) 
$V_1$: Reset token MUST be single-use (invalidated on 1st submit).
$V_2$: Expiration time t_exp MUST NOT exceed 15 mins (t_now - t_created <= 900s).
$V_3$: Token payload MUST hash user_id + password_hash (invalidated if pwd changes).
$V_4$: Rate-limit token requests: max 3 requests per IP per hour.
Optimization & Mechanics

Token Efficiency & Caveman Notation

How ICM achieves up to 75% reduction in context window token usage compared to monolithic system prompts while maintaining absolute execution precision.

Monolithic System Prompt

All instructions, personas, and guidelines loaded on every single LLM call.

~15,000 Tokens

High cost, high latency, context dilution & instruction drift.

Global Skills Setup

Skills loaded from local user config folders when activated by agent heuristics.

~4,500 Tokens

Not portable, invisible in git code review, platform dependent.

ICM Workspace Template

Progressive stage loading + compressed Caveman notation contract encoding.

~1,100 Tokens

100% Portable, zero global config, git-versioned.

Caveman Encoding Syntax

Each CONTEXT.md stage contract uses Caveman notation to replace verbose prose with mathematical and logical symbols:

Symbol Meaning Example Usage
! MUST / Required ! reach Confidence Score ≥85 before proposing approaches
⊥ FORBIDDEN / Never ⊥ generate code before SPEC.md updated & approved
→ Leads to / Yields Idea → Draft SPEC.md & DESIGN.md
∀ For all / Every ∀ UI proposal ! present via visual companion
∃ Exists / Has ∃ enabled visual companion → present mockups

Portability in Action

Applying SDD to Any Repository

Copy Wilberto Lopez's ICM template into any existing or new project in seconds. No global config or IDE extension required.

Step 1: Copy Template Files

Copy the .cursorrules, CLAUDE.md, and specs/ directory into your project root: 

cp -r /path/to/skills/icm-workspace-template/{.cursorrules,CLAUDE.md,specs} ./your-project/

Step 2: Prompt Your Agent

Open your project in Cursor, VS Code, Gemini CLI, or Claude Code, and issue your prompt: 

"Agent, please start the project by reading specs/.sdd/WORKSPACE_ROUTING.md and beginning Stage 01."
